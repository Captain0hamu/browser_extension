何をするプロジェクトか

Firefoxでログイン済みのmanabaから資料をダウンロードし、コースIDに対応するローカルフォルダーへ保存する仕組みです。加えて、Firefoxのポップアップから現在manabaで選択できるコースを取得し、~/Documents直下のフォルダーと照合して、設定に追加できる候補を作れます。

大事な分担: 拡張機能はブラウザーのCookieを読めるがローカルファイルを書かない。Pythonサービスはローカルファイルを書けるがCookieを保存しない。両者は 127.0.0.1 のAPIとトークンでつながります。

Web未経験者向けの基礎

このプロジェクトには「画面を作る側」と「ファイル操作をする側」があります。Web開発は初めてでも、前者を小さなGUIプログラム、後者をローカルで動くPythonプログラムだと考えると理解しやすいです。

popup.htmlの末尾にある<script src="popup.js">は「この画面を開いたらpopup.jsも実行する」という意味です。HTMLのid="generate"はボタンにつけた固有の名札で、JavaScriptのdocument.querySelector("#generate")がその名札を使ってボタンを見つけます。

イベント駆動とは

普通のPythonスクリプトは上から下まで実行して終わります。一方、ブラウザーのJavaScriptは画面を表示したあと待機し、クリックなどのイベントが発生したときに登録した処理を動かします。次の形は「generateボタンがクリックされたら、右側の非同期関数を実行する」です。

generate.addEventListener("click", async () => {
  // Cookieを取り、APIへ問い合わせ、画面を更新する
});

asyncとawaitは、ネットワークやCookie取得のような「返事が来るまで時間がかかる処理」を扱うための記法です。await fetch(...)の行では、画面全体を止めずにAPIの返答を待ち、返答後に次の行へ進みます。

HTTP APIとJSON

APIはプログラム同士の窓口です。このプロジェクトではFirefox拡張が客、Pythonサービスが店員です。拡張はURL、HTTPメソッド、ヘッダー、本文を送ります。PythonはステータスコードとJSONを返します。

要素例意味
URLhttp://127.0.0.1:8765/v1/courses/mapping-candidatesローカルサービス内の「対応表候補」窓口
POSTmethod: "POST"データを渡して処理を依頼する操作
HeaderAuthorization: Bearer ...ローカルAPIを勝手なページから使わせない合言葉
JSON本文{"cookies": [...]}キーと値で表したデータ。JavaScriptのオブジェクトに近い。
200成功結果JSONを読んでよい
401 / 4xx失敗ログイン、token、入力などを確認する

127.0.0.1は「このPC自身」を指す特別なIPアドレスです。つまりこの通信は大学サーバーではなく、自分のPCのFirefoxとPythonサービスの間だけで行われます。ただしCookieを本文に含めるので、API URLを安易に外部URLへ変更してはいけません。

Firefox拡張は普通のWebページと何が違うか

普通のWebページは、そのページの権限だけを持ちます。拡張はユーザーがmanifest.jsonで許可した権限を持ち、Cookie、右クリックメニュー、現在のタブなどを扱えます。その代わり、権限を増やす変更は慎重に読む必要があります。ポップアップはアイコンを押している間だけ表示される小さなHTMLページ、background.jsは右クリックを待つための常駐処理です。

おすすめの読み順と実際に追う方法

一度に全ファイルを理解しようとせず、画面上の一操作を入口にしてデータの流れを追います。以下の順にエディタで二画面表示すると分かりやすいです。

  1. extension/popup.htmlを開く。idが付いたボタン・リストを見つける。これは「画面に何が存在するか」です。
  2. extension/popup.jsを開く。generate.addEventListenerから読み始める。画面の入力→Cookie→fetch→表示の順を追う。
  3. service.pyで@app.post("/v1/courses/mapping-candidates")を検索する。同じURLを探せば、JavaScript側とPython側がつながる。
  4. その関数が呼ぶfetch_current_coursesとbuild_mapping_candidatesを読む。前者はネットワーク、後者はローカルフォルダー照合であり、役割が分かれている。
  5. config.pyでSettingsを見る。サービスがどの設定を受け取っているか理解する。
  6. 最後にtests/test_service.pyを見る。「こう動くべき」という短い仕様書として読める。

エディタで名前を右クリックして「定義へ移動」、または全文検索を使うのが有効です。例えばmapping-candidatesを検索すると、バックエンド実装、ポップアップ呼び出し、READMEの説明を横断して見られます。

初めは全ての記号を理解しなくて大丈夫です。「この値はどこで作られ、どこに渡され、何になるか」を一本ずつ追う読み方が最も確実です。特にCookie、course_id、path、tokenの四つを追えるようになると、全体像がつかめます。

二つの処理フロー

1. 資料を右クリックして保存

Firefox: manabaの資料リンクを右クリック
↓
background.js: タブURLの course_123... からIDを読む。Cookie・リンクURL・Refererを集める。
↓
POST /v1/downloads: token、URLのホスト、コースID、保存先を検証する。
↓
service.py: Cookie付きで資料を取得し、設定済みフォルダーへ一時ファイル経由で保存する。

2. 現行コースから対応表候補を生成

manabaを開いたタブで拡張機能アイコンを押す
↓
popup.js: Cookieを取得し、POST /v1/courses/mapping-candidatesへ送る。
↓
fetch_current_courses(): /ct/を取得し、コースリンクからID・表示名を抽出する。
↓
build_mapping_candidates(): 保存ルート直下のフォルダー名と比較し、4分類の結果を返す。
↓
ポップアップ: 一致分だけをコピー可能なTOMLにする。設定ファイルは自動変更しない。

PythonローカルAPIを読む

データモデル

BrowserCookieは拡張から受け取る最小限のCookie情報です。CookieRequestはコース取得用、DownloadRequestは資料保存用です。Pydanticの型と長さ制限により、予想外の入力を早い段階で拒否します。

候補APIの返り値はMappingCandidatesです。中身は以下です。

{
  "matches": [{"id": "123", "name": "Database", "path": "/home/me/Documents/Database"}],
  "unmatched_courses": [{"id": "456", "name": "Networks", "configured_path": null}],
  "registered_courses": [{"id": "789", "name": "Math", "configured_path": "/home/me/Documents/Math"}],
  "unused_folders": ["/home/me/Documents/Old course"]
}

現在のコースを取る仕組み

fetch_current_courses()は、リクエストで届いたCookieをHTTPヘッダーにだけ入れてhttps://tid.manaba.jp/ct/を取得します。応答先が許可ホスト外、または/ct配下でなければログイン切れとして401にします。HTMLはCourseLinkParserで走査し、URL内のcourse_数字とリンク文字列を集めます。

manabaのHTML構造が変わったときは、まずこのパーサーが正しいリンクを拾えるか確認してください。ブラウザーの開発者ツールで/ct/のコースリンクのURLを確認し、必要ならCOURSE_ID_REまたはCourseLinkParserを修正します。

フォルダー照合の仕組み

direct_folders()はsettings.storage_rootの直下だけをiterdir()で列挙し、隠しフォルダー（名前が.で始まるもの）とファイルを除きます。再帰検索しないことが仕様です。

normalized_name()はUnicodeをNFKC正規化し、casefold()した後、空白・_・-を消します。従ってData Base、data_base、DATA-baseは一致します。一方、翻訳、略称、部分一致、似た文字列は推測しません。

同じ名前の現行コースが複数ある場合、一つのフォルダーを二重に候補化しません。先に見つかった一件だけを一致にし、残りは未一致にします。誤った保存先を作るより確認を促すためです。

APIを増やす型

  1. service.pyでリクエスト・レスポンス用のPydanticモデルを作る。
  2. create_app()内にエンドポイントを置く。
  3. 認証が必要なら最初にauthorize(authorization)を呼ぶ。
  4. 外部URL、ファイルパス、Cookieを使うなら既存の検証関数を流用する。
  5. テスト、README、拡張側の呼び出しを同時に更新する。

Firefox拡張を読む

manifest.json

permissionsは拡張ができることの一覧です。cookiesはmanaba Cookie取得、tabsは現在タブの確認、storageはAPI URL/token保存、clipboardWriteは候補TOMLのコピーに必要です。対象ドメインとローカルAPIのURLパターンもここで許可します。

browser_action.default_popupがpopup.htmlを指定します。変更後は一時アドオンを「再読み込み」しないと反映されません。

popup.js

ボタンを押すと、まず現在タブのホストがtid.manaba.jpかを確認します。次にbrowser.cookies.getAll()でCookieを取り、保存済みのAPI URL/tokenとともに候補APIへPOSTします。結果はtextContentで表示しているため、コース名をHTMLとして解釈しません。

tomlString()はJavaScriptのJSON.stringifyで文字列を引用します。JSON文字列の引用規則はTOMLの基本文字列と互換性があるため、引用符や改行を含むコース名でも、コピーする文字列を壊しにくくしています。

background.js

こちらはポップアップとは独立して常駐し、右クリックメニューを登録します。courseId()はタブURLからコースIDを読むため、コース配下ページ以外で保存を試すと止まります。これは資料URLだけを偽装して別コースの保存先を指定させないための第一段階の検査です。API側でも再検査します。

設定ファイルと保存先

実際の設定は通常~/.config/manaba-folder-sync/config.tomlです。MANABA_SYNC_CONFIG環境変数を指定すると別の場所を使えます。読み込みはconfig.pyのload_settings()です。

[storage]
root = "~/Documents"
collision_policy = "rename"

[courses."1234567"]
name = "Database"
path = "~/Documents/Database"

pathは必ずstorage.rootの内部でなければなりません。読み込み時に絶対パスへ解決してis_relative_to()で検査します。候補生成APIは設定に書き込まないので、コピー後に自分で内容を確認し、このTOMLへ追加します。

よくある改造

照合ルールを変える

normalized_name()だけを変えると比較ルールが変わります。例えば括弧内の曜日を無視したいなら正規表現を追加できます。ただし文字を多く消すほど別の授業を誤一致させやすくなります。変更前に、区別したい名前が同じ正規化結果にならないかテストを追加してください。

Documentsのサブフォルダーも探す

direct_folders()のroot.iterdir()をroot.rglob("*")へ変えると実現できますが、同名フォルダー、過去授業、意図しない大規模走査が増えます。やるなら「何階層まで」「重複時はどうするか」を決め、返すパスをユーザーが識別できる表示にしてください。

TOMLの出力を変える

popup.jsのtoml = data.matches.map(...)がコピー形式です。コメントを付ける、絶対パスを~/Documents形式に直す、表示名ではなくフォルダー名をnameへ使う、といった変更はここです。TOMLの引用処理は残してください。

別のmanabaホストに対応する

config.tomlのmanaba.base_urlとallowed_hosts、さらにmanifest.jsonのURL権限、background.js/popup.jsの固定ホスト定数を同時に見直す必要があります。一箇所だけ変えるとCookieが取れない、またはAPIが拒否する状態になります。

テストとデバッグ

Nix環境でテストを実行します。リポジトリ全体がGitに未登録の作業中でも使えるよう、以下ではpath:指定を使います。

nix develop --impure path:/home/nix/dev/manaba-folder-sync --command pytest -q

JavaScriptとmanifestだけ素早く確認するなら次です。

node --check extension/background.js
node --check extension/popup.js
python -m json.tool extension/manifest.json > /dev/null

Pythonの照合ルールはtests/test_service.pyでテストしています。新しい正常系だけでなく、古い授業フォルダーが候補に出ないこと、隠しフォルダーが出ないこと、既登録コースが重複候補にならないことを守ってください。

ブラウザー側の確認手順は、Firefoxで一時アドオンを読み込み、設定画面にtokenを入れ、manabaを開いてアイコンを押す、です。ポップアップを右クリックして「要素を調査」すると、その画面専用の開発者ツールでエラーを見られます。Python側はpython -m manaba_folder_sync.cli serveを起動した端末の出力で確認します。

安全上の約束（改造時に壊さない）

  • Cookieやパスワードを設定ファイル、ログ、画面、永続ストレージへ書かない。Cookieはリクエスト中だけ使う。
  • ローカルAPIは127.0.0.1で待ち受け、tokenなしで操作させない。
  • ダウンロード元・リダイレクト先は許可したHTTPSホストだけにする。
  • コースIDとページURLのIDが矛盾したら保存しない。
  • 保存先がstorage.root外へ出ない検査を外さない。
  • 候補生成は読み取り専用に保つ。自動でconfig.tomlを編集するなら、少なくとも明示確認・バックアップ・構文検証を別途設計する。

迷ったときの基準は「一致しないなら候補にしない」「保存できないなら止める」です。資料が一件保存されない不便さより、別授業のフォルダーへ保存する事故を避ける方を優先しています。
